# ADR-003 请求事实、用量与事务结算分离

状态：Proposed（待实施）。日期：2026-10-02。

## Context / 背景

SpendLog 不能同时代表请求全集、真实用量与账本。失败可能已耗费上游资源，缓存命中不应再收原生成费，异步接受不等于任务完成。当前多处支出写入忽略错误，ApplySpendBatch 的批内去重和跨副本一致性也需要修复。

可控制的是本地事务、唯一键、准入与恢复；无法控制供应商在丢响应后是否已执行。保证范围必须区分本地唯一结算和外部执行结果。

## Decision / 决策

入口 request、业务 execution、上游 attempt、持续 task、usage 和 settlement 使用独立标识与契约。所有已持久化接收请求最终有唯一入口终态；新增用量及对账通过追加事实，不覆写旧终态。

付费工作前在数据库事务中预占所有预算主体。金额使用精确十进制/整数单位，价格、归属与政策固定到提交快照。供应商成本和用户收费分别核算。

首次结算以稳定 charge_identity=(execution_id, charge_kind, charge_scope) 建立数据库唯一保护；usage_version 和 price_version 是证据版本，不能改变首次收费身份。事务中插入新结算、写分录、调整预占/预算、推进相关结算状态及 outbox。更新用量只产生唯一 adjustment_id 的差额分录。

Redis、指标和报表为可重建投影。至少一次消费必须按 event_id 或版本去重。唯一约束提供至多一次，持久化恢复与重试在依赖最终恢复的前提下提供最终完成。

## Consequences / 影响

需要新增事实表、价格快照、账本、预占和 outbox；双写期只有一条链路实际扣款。历史数据缺失保留 legacy/unknown，不用现价补造。恢复过程能够处理“供应商成功、本地写失败”，避免重新生成来掩盖落库故障。

最坏并发下，唯一收费身份与单事务使重复 worker 只有一个新增分录；预算锁和费用上界维持 S+H≤B。没有有限费用上界就不能承诺有限预算绝不越界。没有供应商幂等或查询能力时也不能承诺外部恰好执行一次，应保留 unknown。

## Rejected alternatives / 否决方案

- 成功响应后依次更新多个 spend：中途失败留下部分账。
- 进程 mutex 或先查后写去重：多副本竞争仍能重复累计。
- Redis 作为唯一账务来源：不能靠易失热投影证明最终余额。
- usage_version 改变后再收一次全额：把数据修订变成重复收费。
- 固定 token 补缺失用量：伪造测量且无法核账。
