# 16 添加模型表单

这一版重新设计「添加模型」这一页。前面几版把端点类型拆开之后，表单本身还是旧的：
它在问一些网关根本不需要的问题，而真正要问的那一件事被藏起来了。

## 现在问错了什么

按页面上从上到下的顺序看：

| 现在有 | 该不该有 | 为什么 |
| --- | --- | --- |
| 选择团队 | 删掉 | 团队是**权限**，不是模型属性。模型是全局资源，谁能用它由密钥和团队配额决定，添加时不问 |
| 供应商 | 留下，并挪到最前 | 它决定后面所有格子：凭据、可选的调用方式、预选模型 |
| 团队 BYOK 模型 | 删掉 | 和「选择团队」是同一个问题的另一种问法 |
| 模型访问组 | 删掉 | 同样是权限，在密钥和团队那一侧管 |
| 高级设置 | 删掉 | 里面是 `custom_pricing`、`pricing_model`、`cache_control`，前两个是界面自己的开关，第三个由部署决定 |
| 测试连接 | 删掉 | 它测的是"上游能不能通"，而这件事在保存时就会知道。留着只会让一个失败的保存看起来像配置问题 |
| 手动填 API Base / API Key | 删掉 | 见下 |
| 调用方式 | 留下，改成**下拉单选** | 这是整页的核心问题，现在被埋在最后 |
| 模型价格关联 | **补上** | 见下 |

### 手动填 API Base 和 API Key

"不存在没有供应商的手动填 api_base 的情况"——这是对的，而且理由比"界面上多余"更硬。

一个供应商在目录里登记的是三件事：slug、凭据字段、默认根地址。手填 API Base 等于让每一行自己带一份根地址，于是：

- 同一个供应商的十行模型可以指向十个不同的地址，而没有任何地方能看出它们是一家的；
- `provider.APIBase` 的兜底（部署没填就用供应商默认）失去意义；
- 直通那一档的根地址是**固定的**——方舟内容生成的地址不能改，改了就不是方舟了。允许手填等于允许把这一档改坏。

所以凭据只有一个来源：在添加供应商时填一次，之后每一行模型引用它。

### 模型价格关联

这是现在**完全没有**的一件事，而它是最要紧的一件。

网关按模型名取单价（`catalog.TokenRates`）。名字对不上价目表时，`Cost` 返回 `ok=false`，这次调用**记一行零费用**。也就是说：名字写错一个字符，模型照常能用，账单上是零。没有报错，没有告警。

现在唯一的防线是操作员在凭据那一栏手填「每百万 token 单价」。那是：

- 一个**可选**字段，不填就静默变成零费用；
- 和价目表里的同一个数字重复，两边可以不一致；
- 填的是每百万，存的是每 token，中间差六个数量级。

新的设计把它变成一个**必答的问题**：这条模型对应价目表里的哪一条。

## 重新设计的表单

```
1. 供应商
   [ OpenAI          v ]

2. 模型                        ← 这一步决定价格
   [ gpt-5.6-sol     v ]  或  [ 手动输入 ]
   → 选中之后立刻显示：输入 $5.00 / 输出 $30.00 每百万 token
   → 目录里没有这条时：明确提示"这条不在价目表里"，并要求填单价

3. 调用方式
   [ 对话            v ]
     · 对话        /v1/chat/completions · /v1/messages · /v1/responses
     · 补全        /v1/completions
     · 向量        /v1/embeddings
     · 图像        /v1/images/generations · /v1/images/edits
     · 视频        /v1/videos
     · 语音合成    /v1/audio/speech
     · 语音转写    /v1/audio/transcriptions
     · 重排序      /v1/rerank
     · 审核        /v1/moderations
     · 方舟内容生成   ← 后台登记的直通，按供应商出现
     · 七牛内容生成   ← 同上

4. 单价                        ← 由第 2 步带出，可改
   输入 [ 5.00 ]  输出 [ 30.00 ]   每百万 token
   缓存读 [ 0.50 ]  缓存写 [ 6.25 ]

   [ 保存 ]
```

顺序的理由：供应商定住可选范围，模型定住价格，调用方式定住入口。每一步都收窄下一步。

## 三个决定

### 1. 调用方式是单选，不是多选

之前做成了多选。那是错的。

多选解决的是一个不存在的问题：运维心里想的是"这条模型是干什么用的"，答案只有一个。做成多选会带来两个真问题：

- 一条同时勾了对话和向量的模型，实际上没法验证它两样都能答——界面允许了一个它无法证明的声明；
- 直通本来就只能单选（它的路径是固定的），多选里混进一个单选的东西，控件本身就不自洽。

一条模型要应答多种能力时，建多条模型。这不是负担：它们的单价本来就可能不同。

### 2. 直通和「对话 / 向量 / 视频」同级

它们是同一个问题的不同答案："这条模型怎么被调用"。运维不需要知道哪一个由网关编译、哪一个原样转发——那是实现细节。所以它们在同一个下拉里，中间不分组、不加标题。

界面需要说的只有一件事：选了直通之后，路径和字段已经在网关里定好了，没有要填的格子。

### 3. 直通只能来自后台登记

手填路径表这条设计取消。理由：一份手填的路径表发不出请求，或者发出去拿不到结构化的返回值，于是预选、日志、用量、任务 id 的跟进都没有依据。上游跟对话、图像、视频一样必须是**固定的**，只是它走原样转发。

所以表单里不会出现 API Base / 模型字段 / 任务 id / 路径表这几个格子。要加一家直通，是在 `internal/provider/` 里加一个包。

## 页面：/models-and-endpoints

用同一套顺序重排：

```
模型与端点

  [ 添加模型 ]                                    ← 主按钮，打开上面的表单

  供应商（卡片）
    OpenAI        26 个模型    凭据已配置
    Anthropic     15 个模型    凭据已配置
    ByteDance     17 个模型    缺凭据        [ 配置 ]
    ...

  模型（表格）
    模型              供应商      调用方式    输入      输出      状态
    gpt-5.6-sol       OpenAI      对话        $5.00     $30.00   在用
    qwen3-max         Aliyun      对话        $0.36     $1.45    在用
    deepseek-v3       DeepSeek    对话        $0.58     $2.32    在用

  价格目录（原来的 /price-data）
    内嵌目录 + 手动覆盖，保持现有设计
```

三处变化：

- **供应商在前**，因为它是配置的单位。缺凭据的供应商排在前面并直接给一个「配置」按钮——这是新增模型之前唯一必须先做完的事。
- **调用方式进了模型表**，运维一眼能看出这条模型接的是哪个入口。
- **单价直接从价目表显示**，不再让操作员从别处抄。目录里没有的模型标出来。

## 实现顺序

1. 表单：去掉团队、BYOK、访问组、高级设置、测试连接、手填凭据；供应商挪到最前；调用方式改成单选下拉。
2. 价格关联：模型选择器接价目表，选中就带出单价；目录里没有时要求手填并明确提示。
3. 页面重排：供应商卡片置顶，模型表加调用方式列。
4. 直通那一档保持后台登记，表单里不再有可填的路径。

## 测试

- 表单：默认选中第一个供应商的第一条模型；选中模型后单价自动填上；目录里没有的模型会要求手填。
- 表单：调用方式是单选；选直通之后没有可填的路径格子；提交体里 `transport` 是直通的 id。
- 表单：提交体里不出现团队、访问组、advanced 那些字段。
- 页面：缺凭据的供应商排在最前并且带配置入口。
- 后端：一条名字不在价目表里、也没有手填单价的模型，调用之后日志里是零费用——这条测试用来证明第 2 步解决的问题是真的。
