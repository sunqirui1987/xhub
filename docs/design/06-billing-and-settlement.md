# 06 计费与结算

> **目标设计，不是当前行为。** 本文描述的是计划要实现的架构。现在实际运行的行为见 [docs/current/](../current/)。两份冲突时，以 `current/` 和代码为准。

状态：当前有 catalog.Cost、实体 spend、Redis 热支出及批量日志入库；尚无统一预占、价格版本和账本。证据：internal/gateway/spend.go 的 recordSpend / persistSpend 会忽略部分写错误且分次更新实体；internal/store/spend_batch.go 的 ApplySpendBatch 在同批内未把新 request_id 加入 seen，进程锁也不足以提供多副本幂等。

## 目标与账务边界

分别保存供应商成本 provider_cost 和用户收费 customer_charge。路由失败、供应商重试、缓存命中、退款的收费策略版本化，不能把二者混为同一 spend。用量是事实，金额是该事实与价格版本的计算结果；未知价格不等于免费。

报价使用 currency、unit、unit_price、quantity_basis、rounding_rule、effective_at、price_version、计费维度。金额采用固定精度十进制或指定最小计量单位整数，数据库及 Go 计算均避免 float64 作为账本权威；每行/每单的舍入顺序写入规则。多币种报表分币种返回，汇率换算额另存汇率版本。

## 预算预占

开始付费工作前，根据硬性限制计算费用上界 R，并在同一事务锁定所有关联预算主体（key/user/project/team/org）。锁顺序固定；校验每个主体余额后一起预占，任一不足则全部不写。预算并非按每个主体另收一笔钱：同一费用被投影到多个约束账户，不能相加当成全局总收入。

B 为周期预算，S 为已结算净支出，H 为有效预占之和。准入条件为 S + H + R ≤ B，事务提交后 H 增加 R。上游参数必须限制最大 token、数量、时长和重试费用，使可收费 C ≤ R。结算时 S 增加 C，H 减少 R；释放只减 H；退款追加负向分录并保持可追踪关系。

充分性：初始 S+H≤B，每次准入在锁内维持不等式；结算增量 C−R≤0；释放或退款也不增加，故任意并发顺序下 S+H≤B。下界：无法得到 C 的有限上界时，任何有限 R 都可能被实际费用超出；应禁止该操作，或明示不同的超额承担策略，不能承诺硬预算。流式/长任务要在安全停止前扩展预占，若供应商无法强制截断仍无法给硬上界。

预算周期按明确时区和周期 ID 管理；跨周期长任务的预占和结算归属在提交时固定。不同策略可转移余额但必须有显式分录，不能在午夜把旧预占清零。失效租约只证明 worker 不活跃，不证明上游没收费，未知任务的预占不能自动释放。

## 原子结算

BillingService.Settle(charge_identity, usage_id, price_snapshot_id) 在一个本地事务内处理首次结算。charge_identity=(execution_id, charge_kind, charge_scope)，由它稳定生成唯一 settlement_key；用量和价格版本只作为证据，不能进入收费身份。charge_scope 区分用户收费与具体供应商 attempt 成本，预算主体投影不另建收费身份。

1. 锁定预占与 execution，读取有效用量和锁定的价格快照。
2. 插入唯一 settlement_key；重复键读取已存在结果并核对摘要，冲突内容报警。
3. 写金额分录、终态/结算事实、预算预占释放与 key/user/project/team/org 聚合变化。
4. 写 outbox，提交后再通知 Redis 投影、报表和异步通知。

事件、账本和权威预算投影必须在同一数据库。插入只对本次真正新增的 settlement 累计金额，使用数据库唯一约束和冲突处理，不能“先查是否存在，再无条件加钱”。同批重复输入先规范化并检测内容冲突；跨 worker 唯一约束仍是最终保护。

结算状态包括 reserved、pending_usage、pending_reconciliation、settled、released、adjusted；详见 [结算结构](schemas/settlement.md)。补充对账/退款通过 BillingService.Adjust(settlement_id, adjustment_id, evidence) 写追加分录，引用原分录并沿用原报价；明确的价格纠错必须另附授权、修正报价与原因，普通改价不影响旧单。不能在 usage_version 增加时把全额再收费一遍，只结算差额。

调整同样锁定结算及全部预算账户，以数据库唯一 adjustment_id 去重；差额按已经入账的净额计算，防止两个 worker 同时相对原始金额计算而多收。退款不能超过对应收费的可退净额，也不能反复释放同一预占。保留预占时正向差额必须先消耗剩余预占；已释放风险后发生超出原证明上界的修订，不能绕过预算直接加收，应进入待对账，由明确政策确定平台承担或后续获准收费。硬预算证明只覆盖所有新增收费都受预占或同事务余额校验约束的执行。

## Redis 与未知结果

Redis 用于请求调度、可重建热投影或队列加速，不是最终金额或预算真值。outbox 在数据库提交，至少一次消费，按 event_id 和账户版本更新投影；队列丢失可重建。若仍以 Redis 做强制限流，故障时拒绝新工作或切入已验证的权威替代机制。

未知用量、未知上游结果或缺失价格进入 pending 状态。新收费操作在价格未知时拒绝；已发生的费用进入对账，不设为 0。网关产生的预上游错误无生成费，但仍记录事件。上游失败可能收费，要按真实使用量及用户收费政策结算。政策可以让平台承担错误尝试成本，但不能把实际 provider_cost 抹掉。

## 迁移与验收

先修复批内重复和跨副本唯一约束，再引入账本和预占；从一致性快照导入旧净支出余额，设置 origin=legacy，缺失明细不重造。迁移期间只能有一个权威写链路，影子计算不实际扣款。

验收：同批/跨批/跨进程重复只结算一次；任意事务步骤故障全部回滚；一千次并发争抢不会越过硬预算；未知上游费用保留预占并可对账；改价不重算旧单；多主体投影一致；Redis 清空后金额无变化；金额小数及舍入案例精确。参见 [ADR-003](decisions/ADR-003-request-event-and-settlement.md)。
