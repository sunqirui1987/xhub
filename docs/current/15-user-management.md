# 15 用户管理

状态：创建用户、用户列表和改密码按当前账号模型收过。本文说明现在该怎么建人、人属于哪里、忘了密码怎么办。证据：`internal/iam/users.go` 的 `CreateUser` / `SetPassword` / `StoreRole`，`internal/gateway/identity/handlers.go` 的 `UserNew` / `UserSetPassword`，`internal/authz/decide.go` 的 `decideUserPassword`，`frontend/src/components/CreateUserButton.tsx`，`frontend/src/components/SetPasswordModal.tsx`。

## 先分清两层

一个人身上有两件互不相干的事。

| | 问的是什么 | 存在哪里 | 可选值 |
| --- | --- | --- | --- |
| 账号角色 | 这个人能不能管整站 | `users.role` | `admin` 平台管理员，`user` 普通用户 |
| 团队角色 | 这个人在**某一个团队**里能不能管成员和项目 | `team_members.role` | `team_admin` 团队管理员，`member` 团队成员 |

还有第三层，但它不是账号角色。组织管理员记在 `organization_members`，只对某一个组织生效。同一个人可以是 A 组织的管理员，同时只是 B 组织里某个团队的成员。创建用户时可以直接指定一个组织管理员关系，也可以在组织页面补上。

旧邀请框上那句「此角色独立于任何团队/组织角色，请到设置里配置团队/组织管理员」来自 LiteLLM。它把账号角色和团队角色说成要去别的设置页配。当前产品里，团队角色就在创建时可选的那个团队上，或者之后在团队页的成员里改。

## 创建用户时怎么选

按钮在「用户」页，文案是「创建用户」。没有邀请邮件，也没有邀请链接。平台管理员填邮箱和至少 8 位的初始密码，对方用这两项登录。

一次请求把四件事一起定下来：账号、团队关系、组织管理员关系、预算上限。这些以前是分开的调用，第二步失败就会留下一个建好了却什么都够不到的人。

账号角色默认是**普通用户**。只有这个人要管理组织、全部团队、用户和预算时，才选**平台管理员**。

平台管理员不等于某个团队的管理员。平台管理员要调用模型，仍然要加入一个团队。普通用户也一样：不在任何团队里，就没有模型可用。

「加入团队」可以留空。留空只是建账号，之后到那个团队的成员页，用邮箱加进去，并选择团队成员或团队管理员。

如果创建时就选了团队，还要选「在这个团队里的角色」：

- 团队成员：能用这个团队允许的模型，不能管成员。
- 团队管理员：能改这个团队的名称和说明，能加人和建项目。不能改预算上限，不能删团队，也不能管其他团队。

一个人可以同时在多个团队里，每个团队的角色单独算。他可以是 A 团队的管理员、B 团队的成员，同时账号仍是普通用户。

「预算」默认不限，此时账号继承团队的额度。要单独设上限时打开开关填金额，填 0 也是上限，和不限是两回事。

「设为组织管理员」可以留空。填了就是那个组织的管理员，管理该组织下的全部团队和项目。

## 用户列表怎么读

每一行有两列和归属有关：

- 账号角色：平台管理员或普通用户。
- 所在团队：`团队名 · 团队管理员` 或 `团队名 · 团队成员`。没有团队时显示「未加入团队」。

组织不列在用户行上。打开某个用户，团队卡片列出团队名、所属组织、以及他在这个团队里是团队管理员还是团队成员。他是不是组织管理员，看组织页面的「组织管理员」。要改团队角色，去那个团队的成员页，或在创建时选「在这个团队里的角色」。

组织管理员管理这个组织里的团队（名称、成员、项目）。组织的预算上限和删除组织仍只有平台管理员可以做。一个组织可以暂时没有组织管理员，平台管理员仍然管得到它。完整的判定、列表范围和密钥规则见 [16 权限](16-permissions.md)。

## 忘记密码时怎么办

管理员直接设新密码，不发链接。

用户页每一行的「重置密码」打开一个设置新密码的对话框，填两次，保存。这取代了以前那个「重置密码链接」：那个链接指向 `/ui/onboarding`，而后端既没有签发 token 的处理器，`claim_token` 又会把 `password` 字段丢掉，所以链接打不开、就算打得开也改不了任何东西。

谁能改谁的密码，比「能改角色」窄一层：

| 谁 | 能改谁 |
| --- | --- |
| 平台管理员 | 任何账号 |
| 组织管理员 | 本组织任意团队里的人 |
| 团队管理员 | 自己管理的团队里的人 |
| 普通成员 | 只能改自己的（走个人资料） |

团队管理员不能改平台管理员的密码，也不能改组织管理员的密码——那两个账号够得到的东西比这个团队大，接管它们等于越权。判定写在 `internal/authz/decide.go` 的 `decideUserPassword`，用的是数据库里的实时成员关系，请求里说的团队一律不算数。

改完立刻生效：`SetPassword` 会把 `session_version` 加一，对方已经登录的会话下一次请求就失效。新密码仍然是至少 8 位，这条规则和 bcrypt 一起放在 `iam.hashPassword`。

## 不要在用户页做的事

这些请求网关不会执行，页面上不再收集：

- 发邀请邮件、生成邀请链接。账号只能由平台管理员用密码创建，密码由管理员直接交给本人。
- 在账号上单独勾选「团队之外的模型」。模型范围来自团队，再被项目和密钥收窄。
- 默认用户设置。没有一套创建时自动套用的全局用户模板。

编辑用户时，账号角色同样只有平台管理员和普通用户。改他在某个团队里的角色，去那个团队的成员页。

## 网关

`POST /user/new` 认 `user_email`、`user_alias`、`password`、`user_role`，另外可选 `max_budget`、`team_id`、`team_role`。组织管理员不在这里任命，去组织页的「组织管理员」。`user_role` 写成 `admin` 或 `proxy_admin` 都存成平台管理员；空、`user`、`internal_user` 都存成普通用户。别的角色字符串会被原样拒绝。

密码短于 8 位会失败。创建成功不会返回邀请链接。

账号和它的成员关系在同一个事务里写。任何一步失败都整体回滚，不会留下一个建好却够不到东西的账号。`team_role` 和 `team_id` 只给一个、或者给了一个不存在的团队，都是 400。

`POST /user/set_password` 带 `user_id` 和 `password`，给某个账号换密码。返回里没有密码。`POST /user/{user_id}/password` 是同一个处理器的路径形式。授权用 `authz.ActionUserPassword`，和改角色的 `ActionUserWrite` 分开，因为能改角色的人和能改密码的人不是一批。

`GET /user/list` 的每个用户带 `teams`：`team_id`、`team_alias`、`user_role`。这里的 `user_role` 是团队角色，不是账号角色。这个列表按调用者的可见范围收窄：平台管理员看全部，组织管理员看本组织的人，团队管理员看自己团队的人，其他人只看到自己。
