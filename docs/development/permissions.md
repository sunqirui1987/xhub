# 权限规则

[开发指南](README.md) · [客户使用与管理](../user-guide.zh-CN.md)

控制台只负责把按钮藏起来或亮出来；每一次请求仍由网关重新判定。证据：`internal/authz/decide.go` 的 `authorize` / `decide` / `decideUserPassword`，`internal/authz/authz.go` 的 `Guard`，`internal/iam/schema.sql`，`internal/gateway/identity/handlers.go`。端到端的可见范围由 `internal/gateway/visibility_chain_test.go` 和 `frontend/e2e/visibility-chain.spec.ts` 逐层验证。

## 1. 一次请求怎么被挡住

顺序固定，不能跳。

1. 认出凭据。没有凭据、凭据无效、账号已停用、会话版本已经变过，回答 **401**。
2. 如果这个动作针对一行已经存在的数据，先从数据库读出它属于哪个团队、哪个组织、是不是封禁。读失败回答 **500**，不当成「没有权限」。读不到这行回答 **404**。
3. 团队或组织处于 `blocked` 时，普通会话一律 **403**。只有平台管理员还能操作，用来把封禁打开。
4. 按下面的矩阵判定。判定用的是**这一次请求**读到的成员关系，不看登录时的缓存。
5. 列表不把全表取回来再过滤。SQL 里就带上范围。范围算不出来时用一条永远为假的条件，而不是不加条件。

两种拒绝不要混：

| 回答 | 含义 |
| --- | --- |
| 403 | 调用者知道这个对象存在，但是这个动作不允许。例如成员想改团队名称。 |
| 404 | 调用者不该知道这个对象在不在。例如成员去读另一个组织的团队，或者去读别人的个人密钥。 |

虚拟密钥永远不带管理权。谁创建的密钥都一样：密钥只能推理，以及读取它自己那一行。

主密钥不能登录控制台，不能推理，不能列团队。它只用于首次建立平台管理员和应急读取。

## 2. 看见的范围

四层，从大到小。外层能看见内层的全部，内层看不见外层。

| 谁 | 用量 | 用户 | 日志 | 团队和项目 |
| --- | --- | --- | --- | --- |
| 平台管理员 | 所有人 | 所有账号 | 所有请求 | 全部 |
| 组织管理员 | 这个组织下面每个团队的全部用量 | 这些团队里的人 | 这些团队里的全部请求，包括成员的个人调用 | 这个组织下面的团队和项目 |
| 团队管理员 | 这个团队的全部用量 | 这个团队里的人 | 这个团队里的全部请求，包括成员的个人调用 | 这个团队和它的项目 |
| 个人 | 只有自己的 | 只有自己 | 只有自己的个人调用 | 自己加入的团队和项目，不能看别人的用量和日志 |

一个人同时是组织管理员和另一个团队的普通成员时，两套范围叠在一起：组织下面看全部，只参加的那个团队里只看自己。

密钥本身的秘密串仍然只有本人和平台管理员能读。团队管理员能看见这个团队里的调用日志和用量，不能把别人的密钥抄出来。

## 3. 三层身份

一个人身上可以同时有三层。三层各问各的，不能用其中一层代替另一层。

| 层 | 存在哪里 | 值 | 问的是什么 |
| --- | --- | --- | --- |
| 账号角色 | `users.role` | `admin` 平台管理员，`user` 普通用户 | 管不管整站 |
| 组织管理员 | `organization_members.role = org_admin` | 只有这一种有意义的行 | 管不管这一个组织里的团队 |
| 团队角色 | `team_members.role` | `team_admin` 团队管理员，`member` 成员 | 在这一个团队里管不管成员和项目 |

组织没有「普通成员」这层。一个人能看见一个组织，是因为他加入了这个组织下面的某个团队，或者他是这个组织的组织管理员。

平台管理员不需要在 `organization_members` 里有一行。账号角色已经覆盖全部组织。

同一个人可以是 A 组织的组织管理员、B 组织里某团队的成员，账号仍然是普通用户。

控制台登录后侧栏上的 Admin / Internal User，是账号角色的显示名。网关新会话写成 `proxy_admin` / `internal_user`，旧会话可能仍是 `admin` / `user`。两种拼写指的是同一层，都不是团队角色，也不是组织管理员。

## 4. 平台管理员

账号角色 `admin`。会话判定见 `Guard.PlatformAdmin`：必须是会话，且角色是 `admin`。

可以：

- 创建、禁用、删除账号，改账号角色和账号预算。创建时可以一并指定团队、团队角色、组织管理员关系和预算，整个写入在一个事务里。不能删除自己。停用或改角色会使对方的会话版本加一，旧登录立即失效。
- 给任何账号设新密码。改完 `session_version` 加一，对方已登录的会话下一次请求失效。
- 创建、改名、改预算、删除组织。删除组织时如果下面还有团队，会拒绝。
- 创建团队、删除团队、把团队换到另一个组织、改团队的模型列表和预算上限、封禁团队。
- 在任何团队里加人、改团队角色、移除成员。
- 在任何团队里建项目、改项目、删项目。
- 读取任何人的个人密钥，管理任何团队的服务密钥。读到别人的请求正文时会写一条审计。
- 看全部用量、全部请求日志、审计日志。

模型列表留空表示这个团队不限制模型。团队模型列表和封禁状态只有平台管理员可以修改；团队金额、RPM、TPM 由平台管理员或所属组织管理员分配。

## 5. 组织管理员

一行 `organization_members`，角色 `org_admin`。由平台管理员或该组织现有的组织管理员，用对方的准确邮箱任命。撤销只是删掉这一行。一个组织可以暂时没有组织管理员，平台管理员仍然管得到它。

可以：

- 看见这个组织，并改它的名称。
- 任命或撤销这个组织的其他组织管理员。
- 看见这个组织下面的全部团队，即使自己不是这些团队的成员。团队列表走 `ListVisibleTeams`。
- 改这些团队的名称和说明。
- 在本组织创建团队，并在组织额度内分配各团队的金额、RPM、TPM。三项分别校验，下级固定分配总和不能超过上级；空值共享剩余容量，零值禁止消费或调用。
- 在本组织团队内分配个人的金额、RPM、TPM，个人仅能分配自己的 API Key 额度，不能自行扩大个人上限。
- 在这些团队里加人、改团队角色、移除成员。移除仍要留下至少一位团队管理员。
- 在这些团队里创建、修改、删除项目。创建时网关会先读出团队所属的组织，再判定是不是这个组织的管理员。
- 看见这些团队的项目列表。
- 给这些团队里的人设新密码。这是唯一一项比团队管理员宽的管理动作：团队管理员只能改自己管的那个团队里的人的密码，组织管理员能改本组织全部团队里的人的密码。

不可以：

- 改组织预算，删除组织，新建组织。这三件事是 `ActionOrgWrite`，只有平台管理员。
- 删除团队、把团队换组织、改团队模型列表、封禁团队。这几件是 `ActionTeamDelete` / `Move` / `Models`，只有平台管理员。跨组织创建团队或修改三项额度也不允许。
- 读别人的密钥秘密串。密钥本身只有本人和平台管理员能读。组织管理员看见的是这个组织下面的用量和请求日志，不是密钥。

`/auth/me` 里，组织管理员会带上 `teams.read`、`teams.manage`、`members.manage`、`projects.manage`。不会因为这一层身份带上 `keys.service` 或 `usage.team.detail`。

## 6. 团队管理员

`team_members.role = team_admin`。只在这一个团队里生效。

可以：

- 改这个团队的名称和说明。
- 看成员列表，用准确邮箱把**已经存在**的账号加进来，并指定团队成员或团队管理员。邮箱不存在和账号已停用是同一种错误，避免拿这个接口探测有哪些账号。
- 改成员的团队角色，移除成员。团队必须留下至少一位团队管理员，否则 400，正文是 `team must keep at least one team_admin`。移除会立刻作废这个人在该团队下的个人密钥。服务密钥属于团队，不动。
- 创建、修改、删除这个团队的项目。项目的模型列表必须落在团队允许的范围内。项目预算不能高于团队预算上限。
- 创建、轮换、停用、删除这个团队的服务密钥。
- 给这个团队里的人设新密码。不能给平台管理员、也不能给组织管理员设密码：那两个账号够得到的东西比这个团队大。
- 看本团队全部用量，包括每个成员的。
- 看本团队全部请求日志，包括成员用个人密钥发出的调用。

不可以：

- 改团队模型列表、团队预算上限、封禁、删除团队、把团队换组织。
- 读其他成员的密钥秘密串。他们的用量和请求日志在这个团队范围内是可以看的。
- 创建账号、改别人的账号角色、管理组织预算。
- 给平台管理员或组织管理员设密码。
- 把别人设成平台管理员。团队角色只能是 `team_admin` 或 `member`。

## 7. 团队成员

`team_members.role = member`。

可以：

- 看自己所在的团队、这个团队所属组织的名称、成员列表上的名字和角色、项目列表。
- 为自己创建个人密钥。密钥必须绑在自己所在的团队上，模型只能在团队（以及所选项目）允许的范围内收窄，不能扩大。
- 看自己的个人密钥、自己的用量、自己的请求日志。看不到同团队其他人的用量和日志。

不可以：

- 改团队、改成员、改项目、看服务密钥、看别人的日志。
- 在自己不属于的团队里建密钥。密钥上如果指定了项目，项目必须属于这个团队。

一个人不在任何团队里，就没有模型可用。平台管理员也一样：要调用模型，仍然要加入一个团队，或者走他自己有权使用的密钥。

## 8. 密钥

两种所有者，存在 `api_keys.owner_type`。

| | 个人密钥 `personal` | 服务密钥 `service` |
| --- | --- | --- |
| 属于谁 | 一个账号，并且绑一个团队，可选一个项目 | 团队或项目，没有所属用户 |
| 谁可以建 | 本人，在自己的团队里。平台管理员可以建 | 该团队的团队管理员，或平台管理员 |
| 谁可以读 | 本人和平台管理员 | 该团队的团队管理员和平台管理员 |
| 成员被移出团队 | 他在这个团队下的个人密钥作废 | 不动 |
| 用来做什么 | 推理，以及读自己这一行 | 推理。密钥本身不能打开管理接口 |

虚拟密钥每次请求都重新检查：拥有者仍是启用状态、仍是该团队成员、团队和项目没有封禁、密钥没有作废。这些变化在下一次请求就生效，不等密钥过期。

## 9. 模型和预算怎么收窄

路由模板选择另外检查模板本身的可见性。平台模板可读；组织模板只在该组织可读；团队模板只在该团队及其上级组织管理范围可读。组织、团队和密钥保存、服务密钥创建、密钥批量更新和专用 binding API 均在修改前执行这项检查，不允许仅凭另一租户的模板 ID 绑定。清空选择表示继承。存储错误不能视为模板不存在或授权成功。证据：`internal/gateway/templateauth/selection.go` 和 `internal/gateway/template_selection_regression_test.go`。

调用时实际能用的模型，是从外向里交出来的，不会逐层放大。

- 团队的 `models` 为空：不限制，可以使用已发布的模型。
- 团队的 `models` 有值：团队以及它下面的项目、密钥都只能使用这些模型。
- 项目的 `models` 为空：沿用团队。有值：必须是团队允许集的子集。
- 密钥的 `models` 再在项目或团队的允许集里收窄。

金额、RPM、TPM 按组织 → 团队 → 个人 → API Key 分配，每个维度的固定分配总和不能超过上级容量；共享项只能使用未保留给固定项的剩余容量。组织上限由平台管理员设置；本组织团队上限由组织或平台管理员设置；团队内个人上限由所属团队、组织或平台管理员设置；个人可以在自己的额度内分配 API Key。项目预算仍单独校验不能高于团队预算。完整语义见[配额管理](../quota-management.md)。

真实验收清单分别声明 `own_team_limits`、`foreign_team_limits`、`team_models_update` 和 `team_status_update`，不能将团队额度与模型权限合成一条旧的“平台专属”断言。权限验收对金额、RPM、TPM 分别发送原值写回请求，避免改变保留数据的路由或分钟限制；实际新额度保存、超配拒绝和数据面拦截由后台 regression 与浏览器 E2E 验证。

账号上没有一份独立于团队的模型列表。用户页上的「所在团队」才是他能用哪些模型的来源。

## 10. 列表的范围

单条判定和列表范围是两套代码，必须一致，否则会出现「知道编号能打开，列表里却没有」或者相反。

| 列表 | 平台管理员 | 其他人 |
| --- | --- | --- |
| 团队 `GET /team/list` | 全部。带 `user_id` 时只看那个人的成员关系 | `ListVisibleTeams`：自己加入的团队，加上自己管理的组织下面的全部团队 |
| 项目 `GET /project/list` | 全部 | 同上这批团队里的项目。请求里再带一个 `team_id` 时，只能缩到这批团队之内，不能借此看到外面的项目 |
| 组织 `GET /organization/list` | 全部 | 自己团队所属的组织，加上自己担任组织管理员的组织 |
| 密钥 | 全部 | 自己的个人密钥，加上自己担任团队管理员的那些团队的服务密钥 |
| 用量 | 全部，或按团队收窄 | 自己的行，加上自己管辖的团队（团队管理员，或组织管理员所辖组织下的团队）里的全部行。只是成员时，指定自己所在的团队也只返回自己的行。指定一个既未加入也不管辖的团队是 404 |
| 请求日志 | 全部。读到别人的个人日志正文会记审计 | 自己的个人日志，加上管辖团队里的全部日志 |
| 用户 `GET /user/list` | 全部账号 | 自己，加上管辖团队里的人。其他人的「所在团队」只保留这些团队 |
| 审计 | 全部 | 403 |

`TeamFilter` 的空值有两种，不能混：

- `nil`：不限制，只有平台管理员会得到。
- 空切片：没有任何团队，查询结果是空的，不会变成「全部」。

## 11. 控制台与验证

控制台从服务器返回的权限和资源范围展示控件。创建账号、修改账号角色、组织额度与团队模型范围只对平台管理员开放；组织管理员可在本组织额度内创建团队并分配团队三项额度，团队管理员可在本团队额度内分配个人额度。创建用户可一次提交账号、团队角色、组织管理员关系及预算，失败时整体回滚。

权限修改应同时核对决策层 `internal/authz/authz_test.go`、HTTP 层 `internal/gateway/visibility_chain_test.go` / `permission_test.go`，以及浏览器的 `frontend/e2e/visibility-chain.spec.ts`。使用[测试指南](testing.md)的可选演示租户验证各层范围，不用不可重建的开发数据库关系作为依据。
